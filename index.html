Why the LSM Tree wins sustained random writes

1 · Random vs sequential

Each B+ Tree insert dirties a leaf page somewhere in the file. Evicting or cleaning that page is a random write: seek + rotational wait (≈ 5–10 ms on an HDD) to write 4 KB. The LSM Tree absorbs the same insert into RAM and writes it later in a long sequential stream at full disk bandwidth.

2 · Cache misses on the write path

A B+ Tree must read the target leaf before modifying it. When the dataset exceeds the cache, most inserts first pay a random read, then later a random write. LSM inserts never read the data files.

3 · The WAL is the same for both

Both engines make writes durable with an append-only log and group commit (on an HDD each commit waits about one platter rotation, so both are capped near ~100 commits/s and batch many requests per commit). The difference is what happens afterwards: the B+ Tree owes the disk a random page write per dirty leaf, the LSM Tree owes a batched sequential flush.

4 · Compaction is the price

LSM write amplification is real — data is rewritten as it moves down levels. But those rewrites are large sequential I/Os. B+ Tree amplification is smaller in theory per page, yet each unit is a 4–16 KB random write for a ~100 B record, and splits add more.

5 · Where LSM can hurt

Push the offered load far beyond what the disk can stream and compaction falls behind: L0 files pile up and the engine slows or stops writes (watch the stall counter). Reads also touch more files. Try the 50% read preset or sequential keys — the gap narrows.

6 · SSD changes the ratio

An SSD removes the mechanical seek, so the B+ Tree improves dramatically, but random page writes still cost more than batched sequential ones and wear flash through write amplification. The LSM Tree stays ahead.
